# blizzard/diablo

Diablo format codecs. Every module here is authored in strict TypeScript under the package
profile; the `.js` files beside them are runtime entries that re-export the build output.

Game data (actors, monsters, GameBalance tables, scenes, worlds, powers, quests, sounds and the other
SNO groups) is decoded with the type registry of the user's own installation: the client's C++ static
initializers build it at start-up, so `src/diablo3-sno` runs them in a small x86-64 interpreter and
reads the structure descriptors back. Field names are not in the executable; members read as their
type and offset, and by name where WhiteoutLib's Diablo III definitions fit the registry
(`src/diablo3-sno/field-names.ts`, generated by `scripts/generate-sno-field-names.mjs`; notice in
`THIRD-PARTY-NOTICES.md`). The registry provider reads the executable through the host's installation files
(`ContributionContext.installationFiles`), so no filesystem permission is asked.
Every SNO file also publishes what it names as a relation graph (`src/diablo3-sno/sno-links.ts`): an
edge to each referenced SNO, and for an effect the hardpoints it spawns at. Animated values (the
particle, trail, rope and light paths) preview as keys: time in the particle's life to value.
A scene's navigation mesh is also published as read-only map layers (`map.layers`, `map.layer-read`):
the height and the flags of each square, in `src/diablo3-sno/scene-layers.ts`.
A scene also opens as a world (`common.view/world-scene-source`, `src/diablo3-sno/scene-world.ts`): its
navigation mesh as the terrain, its own mesh and the markers of its marker sets (`scene-markers.ts`) with
their full quaternions; a marker placing an actor draws the actor's appearance.

This package carries no MK2 tree. Appearance decoding is the MK2 implementation carried over —
it compiled under this profile with no type errors — with the deliberate deviations recorded in
`APP-PORT-PROVENANCE.json`: retargeted imports, normalised decoded zeros, a refusal where
upstream silently dropped a submesh whose indices were out of range, the actor's appearance SNO at
0x24, and one warning per missing bone rather than one per clip.

The MK2 game-discovery copy was replaced rather than copied: it only looked for a `.build.info`
marker that every Blizzard CASC product has, and said so itself. The MK3 provider reads the active
build record and matches the Diablo III product.

Diablo II is not covered. It has no MK3 game subject, and the MK2 Diablo codec directories that
name it (`diablo2-character-model`, `diablo2-dc6`, `diablo2-dt1`) contain a manifest and no source
at all — in MK2 as well, so there is nothing to port. MK2's `diablo3-sno-data` was the same empty
manifest; what it named is now `blizzard/diablo3-sno`.
